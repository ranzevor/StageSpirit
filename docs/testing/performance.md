本文面向性能测试执行与阶段验收，固定首版参考环境、负载、测量口径和退出目标。数值是 D1 至 D6 的设计验收目标，各阶段按本文执行实测。

## 参考环境

| 项目 | 基准条件 |
| --- | --- |
| 操作系统与运行时 | Windows 11 x64、CPython 3.12，准确小版本与依赖使用本次安装制品的锁定版本 |
| 处理器与内存 | 4 个物理核、8 个逻辑线程，16 GiB RAM |
| 存储 | SSD，测试开始时应用数据所在卷至少剩余 20 GiB |
| 外部目标 | 1 个实际播放设备、1 个 VTS 目标、1 个 OBS 目标 |
| 展台 | 1920 × 1080，目标 30 fps，10 个可见 Web 控件与 1 个原生捕获 |

每轮记录实际 CPU、逻辑核数、GPU 与驱动、内存、SSD、音频设备与采样格式、显示刷新率、电源模式、操作系统构建、Python、安装制品、依赖、浏览器、OBS、VTS、模型及适配器版本。测试使用独立运行配置、合成数据和隔离场景。

## 参考负载

所有阶段沿用同一套可重建数据，尚未接入的模块在所属阶段加入，D6 运行完整组合。

| 对象 | 固定输入与节奏 |
| --- | --- |
| 运行配置 | 1 个 profile，启用本阶段适用能力 |
| 平台事件 | Bilibili、YouTube、Twitch 各 1 个连接，合计持续 100 事件/秒，按 34、33、33 分配；正文及必要字段的序列化平均大小为 2 KiB |
| 事件突发 | 每 5 分钟把三连接合计速率提升到 500 事件/秒，持续 5 秒，再恢复 100 事件/秒；速率按接收入口的实际到达量计 |
| 事件初态 | 预置 100 万条历史事件，保留完整业务字段、稳定上游身份及同代际递增 sequence；测试期间继续追加 |
| 接口访问 | 4 个本地 MCP 客户端；runtime_status、operation_get、settings_get 及 core 配置保存各 1 请求/秒，按轮转客户端发起；固定历史查询每秒读取 1 页，每页 200 条 |
| 语音 | 每 10 秒请求 1 次播放，每段 2 至 5 秒，循环使用带已知首音及音频区间的合成文本和 PCM 样本；播放所有者始终为 1 个 |
| 语义配置 | 1 个活动模型、500 条映射，每条 2 个关键词、1 个排除词、1 个参数意图；每段语音含 4 个确定命中区间；每分钟在播放中保存一次等规模新修订 |
| 展台内容 | 2 个聊天、1 个字幕、2 个白板、2 个公告和 3 个静态图像控件；5 个 Web 控件置于原生捕获之前，5 个置于其后；聊天持续消费事件，白板和公告各每秒更新 1 次 |
| 页面读取 | 同时保持 1 个编辑页和 1 个只读输出，历史页固定 200 条；分别记录编辑页、输出各平面和 OBS 中输出的帧指标 |

事件输入每 100 条按固定顺序包含 80 条聊天、10 条付费留言、5 条礼物和 5 条会员样本，按各平台支持的事件类型映射，保留适用字段与金额单位。历史分页分别读取首页、连续续页和已固定上界的末页，使用持续追加条件检查查询。目录分页使用预置的 1 万项本地音色目录，每页 200 条。

规则与故障基准使用可控本地提供方、事件入口及目标协议替身，固定响应、音频、对齐与故障节奏。设备首音、VTS 参数观察和 OBS 内绘制指标分别使用真实设备及目标，替身数据单独作为机制基准统计。语音样本采用 48 kHz、双声道、16-bit PCM，起始为可识别的非静音音频。播放队列空闲且设备已经打开时开始首音基准。实际适配器通过同一公开调用入口运行，记录上游网络、合成、设备、VTS 与 OBS 的完整分段时延及版本。

命令基准通过 settings_save 交替保存两份通过配置 Schema 的等规模 core 设置，每次使用当前 expected_revision，保持数据路径、外部连接及资源预算固定。长操作在本阶段公开命令入口执行，语音与外部动作保持表中节奏，分别观察受理落库与操作详情。输入速率独立于响应时间，客户端在并发上限处记录未能按计划发出的请求，不能通过等待前一请求结束降低实际负载。

## 测量与统计

每轮先预热 5 分钟，再连续统计 30 分钟。核心接口的每个被测入口至少取得 1000 个样本，样本不足时延长统计窗口。全部指标逐入口、逐适配器和逐播放时钟类型分别汇总，保留样本数、吞吐、P50、P95、P99、最大值、失败数、超时数、拒绝数和实际到达率。

分位数将样本升序排列，使用 nearest-rank，即 P95 取第 ceil(0.95 × N) 项，P99 同理。持续负载与 500 事件/秒突发分别汇总，普通时延门限覆盖持续负载；突发按[过载与稳定性](#过载与稳定性)判断。完整测量窗口的全部请求保留在统计中，超时、错误与尚未完成请求单列，并进入完整性核对。基准持续负载下，已配置能力的合法请求应完成且无非预期拒绝。

进程内时间使用单调时钟。跨进程使用同一测量器或经校准的时钟映射，记录校准误差，采集分辨率不大于 1 ms。浏览器与运行时的时钟在每轮开始和结束校准，跨时钟误差不大于 2 ms。playback_clock、alignment_source、clock_epoch、数据代际、连接代际和模型代际随样本保存，时间只在有效时钟域内比较。

核心接口时延从本地 MCP 客户端发出完整请求到取得完整响应，包含传输、校验、序列化和本地存储。长操作的受理响应须已经提交操作账；外部动作完成另按其实际完成点记录。通知与字幕终点分别以客户端收到通知及页面完成对应绘制计时。

实际语音适配器逐项记录请求受理、队列等待、上游连接、合成首包、首个可播放缓冲、完整音频、设备启动和实际首音。外部网络及合成时间计入完整端到端结果，同时与本地控制指标分别列出。原生播放适配器沿用 native_lifecycle 的实际 started 起点；字幕和语义消费者的延迟接收继续使用同一 clock_epoch。

## 过载与稳定性

在参考负载下连续执行 2 小时混合压力测试，预热规则与 30 分钟基准相同。进程资源每秒采样一次，CPU 使用 1 秒窗口。进程退出前采样纳入当前进程树，重新创建的子进程继续计入。

| 对象 | 首版目标与观察 |
| --- | --- |
| 内存 | 主进程与子进程 RSS 合计稳态 P95 ≤ 768 MiB、峰值 ≤ 1 GiB；预热后首 15 分钟与末 15 分钟 RSS 中位值的增长 ≤ 64 MiB |
| CPU | StageSpirit 进程树 CPU 时间增量之和除以采样时长与实际逻辑核数，得到整机容量占比；均值 ≤ 15%，P95 ≤ 30% |
| 页面与外部进程 | 浏览器各页面、OBS、VTS 的 CPU、内存、GPU 占用与整机总占用另列，保留同场时间轴 |
| 事件完整性 | 接收账、持久事件、消费者水位和动作身份可对应；已受理事件无静默丢失 |
| 任务与租约 | 操作、未完成任务、参数租约和分发积压在每次突发后回落；结束、中断、取消和断线按对应场景释放 |
| 突发恢复 | 500 事件/秒的 5 秒突发结束后，10 秒内恢复到持续负载的各项时延目标，继续观察下一完整 10 秒窗口 |
| 显式过载 | 对命令队列、合成、解码、音频缓冲、活跃快照和缓存逐项耗尽预算，按所属契约返回 QUEUE_FULL 或 RESOURCE_LIMIT，核对未受理与已受理结果 |
| 已持久动作 | 队列拥塞、客户端断开和进程恢复均保留原事件动作及操作身份，恢复后按原计划执行或返回明确终态 |

资源配置采用[运行时队列](../design/runtime.md#队列)及[存储预算](../design/storage.md#固定快照与版本回收)的首版默认值。报告每项实际容量、当前占用及峰值，逐项达到上限后验证拒绝、回收和恢复。普通清理保持有效幂等身份、未完成分发和恢复所需记录。

参考事件持续负载在突发中继续持久接收；消费者积压独立计量。超出接收能力的输入显式记录接收失败或接收间断，恢复条件与动作沿用[事件接收规则](../design/events.md#接收与水位)。持久化失败单列错误及受影响事件范围。
